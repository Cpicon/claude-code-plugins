# Design Spec: Fix `<example>` Blocks Breaking Project-Level Agent Discovery

**Issue:** [#9](https://github.com/Cpicon/claude-code-plugins/issues/9)
**Branch:** `fix/issue-9-yaml-parsing`
**Date:** 2026-04-13
**Status:** Approved

---

## Problem

Agents generated by `/agent-team-creator:generate-agent-team` and `/generate-debugger` are silently rejected by Claude Code's project-level YAML parser when saved to `.claude/agents/`. They never appear in `claude agents` or `/agents`. No error is shown.

### Root Cause

The `<` character in `<example>` tags is a YAML flow indicator. In bare multi-line `description:` values (without `|` or `>` scalar indicators), the project-level parser treats `<example>` as invalid YAML and silently rejects the entire file.

The user-level parser (`~/.claude/agents/`) is more lenient and accepts the same format, which is why this was not caught during development.

### Evidence

| Format | Project-level discovery |
|--------|------------------------|
| `description: Simple single-line text.` | Yes |
| `description: >` (folded scalar) | Yes |
| `description: \|` (literal scalar) | Yes |
| `description: Text...\n\n  <example>...` (bare multi-line) | **No** |

## Solution

Replace all bare multi-line `description:` fields containing `<example>` blocks with `description: |` (YAML literal block scalar) using keyword-rich prose.

### Approach

Direct find-and-replace across all affected files in a single pass. No abstraction layer or utility needed — the root cause is a format instruction in documentation/templates, and the fix is changing that instruction.

## Description Format Specification

### Before (broken at project level)

```yaml
description: Use this agent when... Examples:

  <example>
  Context: Something.
  user: "Do something"
  assistant: "I'll do it."
  <commentary>
  This triggers because...
  </commentary>
  </example>
```

### After (works everywhere)

```yaml
description: |
  Use this agent when working on [specific domain], including
  [key file/directory 1], [key file/directory 2], and [feature area].
  Covers [capability 1], [capability 2], and [capability 3].
```

### Format Rules

1. Always use `description: |` (literal block scalar)
2. First sentence starts with "Use this agent when..."
3. Include specific trigger keywords the model can match on
4. List concrete capabilities/domains the agent covers
5. Keep under 5 lines — concise but keyword-rich
6. No XML-like tags (`<`, `>`) anywhere in the value
7. Indent content by 2 spaces under `description: |`

### Trade-off

Dropping `<example>` blocks from the `description` field reduces auto-triggering accuracy. However, project-scoped agents are primarily dispatched by an orchestrator (which knows when to call them), and keyword-rich prose provides sufficient matching for direct invocation.
