# Debugging Report

**Date**: 2026-02-19 21:00
**Issue**: Users can register with the same email address - duplicate email check is not working properly

## Issue Summary
- **Reported Issue**: The email duplicate validation in user registration does not prevent users from registering with an already-used email address. The check silently passes and allows duplicate records.
- **Affected Components**: User registration endpoint (`POST /users`), email duplicate check loop (lines 77-81), in-memory user storage (`users_db`), user ID counter (`user_id_counter`)
- **Severity**: **HIGH**

## Root Cause Analysis

- **Root Cause**: **Off-by-one error in the email duplicate check loop** at `/Users/christianpiconcalderon/PycharmProjects/claude-code-plugins/docs/app/main.py:78`

- **Technical Explanation**:
  The email validation loop iterates over `range(0, user_id_counter)`, which produces user IDs starting at `0`. However, user IDs in this application start at `1` because `user_id_counter` is incremented **before** being used as the storage key (line 86). This creates a systematic mismatch:

  1. **Range starts at the wrong value**: `range(0, ...)` starts at `0`, but no user is ever stored at key `0`. The first user is stored at `users_db[1]`.
  2. **Range ends one too early**: `range(..., user_id_counter)` excludes `user_id_counter` itself (Python range is exclusive on the upper bound), which means the most recently created user is always excluded from the check.

  **Combined effect**: The range `[0, user_id_counter)` is shifted by exactly one position from the actual range of user IDs `[1, user_id_counter]`. This means:
  - The very first registered user's email is **never** checked against (it is always missed).
  - Every subsequent user's email check misses the most recently registered user.

- **Execution Trace (proving the bug)**:

  | Step | `user_id_counter` before | Range checked | IDs in `users_db` | Missed ID |
  |------|--------------------------|---------------|--------------------|-----------|
  | 1st user registers | 0 | `range(0, 0)` = [] (empty) | {} (none yet) | N/A |
  | 2nd user (same email) | 1 | `range(0, 1)` = [0] | {1: user1} | **1** |
  | 3rd user (same email) | 2 | `range(0, 2)` = [0, 1] | {1: user1, 2: user2} | **2** |
  | 4th user (same email) | 3 | `range(0, 3)` = [0, 1, 2] | {1: .., 2: .., 3: ..} | **3** |

  - At step 2: the loop checks `uid=0`, which does not exist in `users_db`, so the `uid in users_db` guard on line 79 evaluates to `False`. User 1's email at `users_db[1]` is never compared. The duplicate passes through.
  - At step 3: the loop checks `uid=0` (not in db) and `uid=1` (in db, catches duplicate of user 1's email). But `uid=2` is never checked. If the email matched user 2 but not user 1, the duplicate would still pass through.

  **Key insight**: The range is always exactly one position behind the actual stored IDs. This means the most recently created user is systematically excluded from duplicate validation.

- **Contributing Factors**:
  - The ID counter is incremented *before* use as a key (`user_id_counter += 1` on line 86, then stored at `users_db[user_id_counter]` on line 95), making IDs 1-indexed while the range on line 78 is 0-indexed
  - The `uid in users_db` guard on line 79 silently skips missing keys instead of raising an error, masking the off-by-one issue
  - The username validation on lines 71-73 uses `.values()` iteration (which works correctly), making the inconsistent email check pattern non-obvious during review
  - No unit tests exist to catch this edge case

## Impact Assessment

- **Direct Effects**:
  - Multiple users can register with the same email address, violating the expected uniqueness constraint
  - Data integrity is compromised -- email addresses should function as unique identifiers
  - If email-based features are added later (password reset, email login, notifications), they will malfunction or target the wrong user
  - Privacy risk: users may receive information intended for another account

- **Side Effects & Warnings**:
  - **Username validation works correctly** (lines 71-73) and is unaffected
  - The **first user ever registered** is never validated against -- their email can always be duplicated by the next registration
  - The **most recent user** at any given point is always excluded from the check, creating a rolling gap
  - If user IDs are ever reused after deletion, the `uid in users_db` guard could cause additional missed checks
  - The soft delete bug (lines 169-173) compounds this issue: deleted users retain their email in `users_db`, which could block legitimate re-registrations once the email check is fixed

- **Risk Level**: **HIGH**
  - Core registration validation failure (duplicate prevention does not work)
  - Data integrity violation affecting 100% of registration attempts
  - No immediate data loss or security breach, but creates a foundation for authentication and authorization problems

- **Users Affected**:
  - All users who register (100% of the registration flow is affected)
  - Particularly impacts users who retry a failed registration or share an email across accounts

## Solutions (Ordered by Effort)

### 1. Quick Fix (Low Effort)
- **Change**: Correct the range boundaries to match actual user ID space
- **File**: `/Users/christianpiconcalderon/PycharmProjects/claude-code-plugins/docs/app/main.py:78`
- **Code Change**:
  ```python
  # Change FROM (line 78):
  for uid in range(0, user_id_counter):

  # Change TO:
  for uid in range(1, user_id_counter + 1):
  ```
- **Why it works**: User IDs start at `1` and go up to `user_id_counter` (inclusive). `range(1, user_id_counter + 1)` covers exactly `[1, 2, ..., user_id_counter]`, matching every stored user.
- **Trade-offs**:
  - Still uses an ID-based loop that is fragile if IDs are ever non-contiguous (e.g., after hard deletions)
  - Still O(n) complexity for what could be an O(1) lookup
  - Leaves the code inconsistent with the username validation pattern

### 2. Proper Fix (Medium Effort)
- **Change**: Use the same `.values()` iteration pattern as the username validation
- **File**: `/Users/christianpiconcalderon/PycharmProjects/claude-code-plugins/docs/app/main.py:75-84`
- **Code Change**:
  ```python
  # Replace lines 75-84 with:
  # Check if email already exists
  for existing_user in users_db.values():
      if existing_user["email"] == user.email:
          raise HTTPException(status_code=400, detail="Email already registered")
  ```
- **Why it works**: Iterating over `.values()` checks every user in the database regardless of their ID. No index arithmetic means no off-by-one errors are possible. This is exactly how the working username check operates.
- **Benefits**:
  - Consistent with the existing username validation pattern (lines 71-73)
  - Immune to off-by-one errors and non-contiguous ID issues
  - More readable and maintainable
  - Eliminates the `email_exists` flag and separate conditional
- **Trade-offs**:
  - Still O(n) per registration, but correct
  - Does not address the broader architectural concern of efficient lookups

### 3. Comprehensive Fix (High Effort)
- **Change**: Introduce an email-to-user-ID index for O(1) duplicate checks, and refactor the combined username/email validation
- **Files**:
  - `/Users/christianpiconcalderon/PycharmProjects/claude-code-plugins/docs/app/main.py:17-18` -- add email index
  - `/Users/christianpiconcalderon/PycharmProjects/claude-code-plugins/docs/app/main.py:65-84` -- refactor validation
  - `/Users/christianpiconcalderon/PycharmProjects/claude-code-plugins/docs/app/main.py:86-95` -- update index on creation
  - `/Users/christianpiconcalderon/PycharmProjects/claude-code-plugins/docs/app/main.py:162-173` -- update index on deletion
- **Code Changes**:
  ```python
  # At line 18, add an email index:
  emails_index: dict[str, int] = {}   # email -> user_id mapping
  usernames_index: dict[str, int] = {}  # username -> user_id mapping

  # Replace lines 70-84 with:
  if user.username in usernames_index:
      raise HTTPException(status_code=400, detail="Username already exists")
  if user.email in emails_index:
      raise HTTPException(status_code=400, detail="Email already registered")

  # After line 95 (storing the user), update indexes:
  emails_index[new_user["email"]] = user_id_counter
  usernames_index[new_user["username"]] = user_id_counter

  # In delete_user (line 170), update indexes:
  if user["email"] in emails_index:
      del emails_index[user["email"]]
  if user["username"] in usernames_index:
      del usernames_index[user["username"]]
  user["is_active"] = False  # Also fix the soft delete bug
  ```
- **Benefits**:
  - O(1) lookup for both email and username uniqueness
  - Scalable architecture for growing user bases
  - Foundation for email-based features (password reset, login by email)
  - Fixes the related soft delete bug (lines 169-173) at the same time
  - Clear separation of concerns with indexed access patterns
- **Trade-offs**:
  - Requires maintaining index consistency across all mutation operations (create, delete, update)
  - Slightly more code to maintain
  - Should be accompanied by unit tests to verify index consistency

from main import app, users_db, user_id_counter

    """Reset state before each test."""

def test_duplicate_email_rejected_immediately():
    """First duplicate attempt must be caught (not just subsequent ones)."""

## Additional Notes

### Why This Bug Is Particularly Subtle
1. **The code looks correct at a glance** -- there is a loop, a conditional, and an HTTPException for duplicates
2. **It partially works**: if three or more users exist, the check will catch duplicates of users 1 through N-2. Only the most recent user is systematically missed.
3. **The username check works perfectly** using a different (correct) pattern on lines 71-73, which makes the email check appear consistent in casual review
4. **The `uid in users_db` guard** on line 79 silently absorbs the wrong key lookups (`uid=0`) instead of raising a visible error
